# H.264 参考帧警告排查与修复

日期：2026-11-05。项目：`E:\横向项目-目标检测\person_tracking`。保留了原录像、原 442 张待复核样本和历史回放；未训练模型。

## 1. 警告含义与本次结论

```text
reference picture missing during reorder
Missing reference picture, default is 2
mmco: unref short failure
```

这些信息来自 OpenCV 使用的 FFmpeg H.264 解码器。H.264 的部分画面依赖其他参考图像；在重排或管理参考图像时找不到预期图像，就可能产生这些警告。它不是 YOLO 权重加载或 CUDA 报错；但“成功返回图像”也不等于图像一定完整。

本次已在 D01 随机跳转时复现，而从头顺序解码的对照没有同类警告。跳转解码路径是本次已确认的触发条件，尚不能由此排除原码流、录像导出或 GOP/关键帧结构的问题。没有关闭或过滤 FFmpeg 日志。

另发现实际视频呈现时间戳（PTS）与“累计帧号 ÷ 标称 25 fps”不一致。因此修复同时涉及参考帧上下文和视频计时，两者需要分别理解。

## 2. 对照证据

诊断目录：`runs/h264_diagnosis/`。环境：`D:\Anaconda\envs\crane-person\python.exe`，OpenCV 4.11.0。

### 2.1 解码警告

| 视频 | 读取方式 | H.264 警告行数 | 是否返回图像 |
|---|---|---:|---|
| D01 | 从头连续读取前 76 帧 | 0 | 是 |
| D01 | 直接跳转到 OpenCV 帧位置 68500 | 12 | 是 |
| D01 | 提前约 2 秒跳转，再读到位置 68500 | 12 | 是 |
| D03 | 从头读取、跳转到 37775、提前约 2 秒预读 | 各 0 | 是 |

证据：`probe_results.json`，以及 `D01_seek.stderr.log` 等对应 stderr 文件。简单增加 2 秒预读并未在该 D01 测试中消除警告，因此没有将“提前几帧跳转”作为默认修复。

### 2.2 累计解码帧号与视频时间不同

| D01 从头累计的 0 起始帧号 | 实际 PTS / 秒 | 帧号 ÷ 25 / 秒 |
|---:|---:|---:|
| 0 | 0 | 0 |
| 10000 | 400.896 | 400 |
| 30000 | 1202.686 | 1200 |
| 68500 | 2746.134 | 2740 |

直接向 OpenCV 请求帧位置 68500 后，返回的位置号为 68501，PTS 却是 2740 秒。可见返回位置号符合请求，不足以证明已定位到“从头累计的第 68500 帧”。证据：`presentation_times.json`。

最初左右对照图 `seek_vs_sequential.jpg` 的两幅画面分别对应约 2746.134 秒与 2740 秒，烧录时钟也相差约 6 秒。它们不是同一时刻，不能用该图的像素差判断花屏或解码损坏，也不能将这 6.134 秒直接解释成“按时间 seek 必然偏移 6 秒”。

新版顺序读取按 **2740 秒 PTS** 定位时，从头累计帧号为 **68347**。这才是与“请求视频时间 2740 秒”一致的比较口径。

### 2.3 同一 PTS 的画面核对

随后重新顺序解码到 PTS 2740 秒，与此前直接 seek 得到、PTS 同为 2740 秒的原尺寸图像比较：平均和最大绝对像素差均为 **0**，两幅图像完全一致；烧录时钟均为约 `15:57:21`。顺序读取本次 stderr 为 0 行。

这说明本次警告没有改变**被比较的目标帧**，不能由此认定整段录像、所有跳转位置或所有相机均无损。证据：`same_pts_comparison.json`、`same_pts.stderr.log`、`D01_sequential_pts2740.png`；可视对照如下。

## 3. 已实施的修改

1. `track` 和 `sample` 的本地文件默认使用 `--decode-mode sequential`：从头按顺序 `grab()`，只提取所需分析帧；不再为每张样本随机跳转。
2. `--start`、`--duration`、分析取帧率和采样间隔改为依据实际视频 PTS，选择每个目标时刻及之后的首个可解码帧。时间戳有空档时跳过空的目标区间，避免重复图像或集中补帧。
3. 缺失、重复或倒退的 PTS 才按标称 FPS 递推，逐帧标记 `time_basis=nominal_fps_fallback`，摘要记录 `timestamp_fallback_frames`；正常为 `time_basis=file_pts`。
4. 默认模式的 `source_frame` 是从头实际累计的解码帧号，标记 `source_frame_basis=decoded_frame_count`。显式 seek 后的位置号标记 `opencv_position_estimate_after_seek`，不把它当作从头累计帧号。
5. 新采样数据根据实际采到的 PTS 估计录像时刻，应用时间组边界排除，再统一分配 train/val/test；所有机器候选仍待人工复核。
6. 保留 `--decode-mode seek`，用于需要快速开始的预览。它只在初始定位时跳转，后续顺序解码；可能出现同类警告或定位不可靠，不用于默认验证路径。

PTS 是媒体时间，不等于曝光时间；文件名时钟与烧录时钟仍需单独核对，这次修复没有建立四路硬件同步。

## 4. 使用方法与时间代价

在项目根目录 PowerShell 中执行，输出必须使用新目录：

```powershell
Set-Location 'E:\横向项目-目标检测'

# 默认已是 sequential；显式写出便于复现
.\person_tracking\run.ps1 track --cameras D01 --start-clock 15:57:20 --duration 30 --decode-mode sequential --out person_tracking/runs/d01_sequential_demo

# 重新生成独立版本的待复核图片和候选框，不训练
.\person_tracking\run.ps1 sample --interval 30 --decode-mode sequential --out person_tracking/data/person_pts_v2

# 需要快速预览时自行选用，可能再次出现原警告
.\person_tracking\run.ps1 track --cameras D01 --start-clock 15:57:20 --duration 5 --decode-mode seek --out person_tracking/runs/d01_fast_preview
```

顺序模式需要先解码所选起点之前的画面。本机 D01 从头读到约 45 分钟处的诊断约需 52 秒；四路会各自预读，首次出结果可能更慢。终端每累计约 10000 帧会显示一次预读进度。该代价是本地录像定位的预读成本，不代表模型每秒推理帧数。RTSP 直播仍采用原有的持续解码、最新帧缓存及重连逻辑，不从头预读录像。

## 6. 历史数据与异常处理

`data/person_v1/` 的 442 张图片、机器候选和 `runs/smoke/` 等历史回放保持原样。旧元数据基于帧号/标称 FPS，seek 后帧号也有上述限制。图片可以继续人工复核，但正式时间对齐、跨路分组或连续跟踪验收前需重新核对时间，必要时另建新版数据集；不要混用新旧采样序列与 MOT 真值。

顺序解码不能修复原录像中已丢失的参考帧。如果默认方式仍持续报警，或画面有花屏、拖影、停帧，应保留原片与 stderr，检查原始相机录像/导出、关键帧完整性；直播则另查传输丢包和断流。无法可靠判断的图片应排除，不作为已确认无人样本。

OpenCV 读取失败不能可靠区分 EOF 与解码故障，摘要会记录 `reader_finish_reason=eof_or_decode_failure`，不把它描述为已确认正常到达文件末尾。
